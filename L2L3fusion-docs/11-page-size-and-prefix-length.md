# 阶段 11：page size 和前缀长度对 TTFT 的影响

| | |
|---|---|
| 日期 | 2026-09-20 |
| 模型 | Llama-3.3-70B-Instruct-FP8，TP=2 |
| 存储 | GPFS `/zion0`，O_DIRECT |
| 脚本 | `benchmark/hicache/bench_steady_state_l3_probe.py` |
| 前一阶段 | [10 并发预取](10-concurrent-prefetch.md)、[08 归因](08-where-the-180ms-actually-goes.md) |

> **结论一**：固定前缀长度时，**page size 对 TTFT 没有可测影响**。
> 读速度变化 4.8 倍，TTFT 差距完全不跟。
>
> **结论二**：**前缀变长会让差距变大**（16384 → 65536 token，Δ 从 179 涨到 266 ms），
> 但**不是因为读变慢**——驱动因素是前缀长度本身。
>
> 我事先押的"读超过一轮调度会合才开始伤 TTFT"这个模型，**被数据否掉了**。

---

## 1. 实验一：扫 page size

固定命中前缀 16384 token、后缀 5120、单探针逐个发、8 个探针、`io_threads 8`、
`group_size 8`。每档内含 L2 对照臂（page size 也会影响 L2，只有同档对比才干净）。

| page | L2 TTFT | L3 TTFT | **ΔTTFT** | 读 span | 带宽 | extent 数 | extent 大小 |
|---|---|---|---|---|---|---|---|
| 64 | 2730 | 2868 | **+138** | 125.6 ms | 10.1 GiB/s | 5120 | 0.25 MiB |
| 128 | 2736 | 2944 | **+207** | 73.0 ms | 17.6 GiB/s | 2560 | 0.50 MiB |
| 256 | 2697 | 2903 | **+206** | 28.8 ms | 43.3 GiB/s | 1280 | 1.00 MiB |
| 512 | 2752 | 2900 | **+147** | 28.4 ms | 44.0 GiB/s | 640 | 2.00 MiB |
| 1024 | 2754 | 2912 | **+158** | 26.3 ms | 47.5 GiB/s | 320 | 4.00 MiB |

### 读速度变了 4.8 倍，TTFT 没跟

```
读 span   26.3 → 125.6 ms      （4.8 倍）
带宽      47.5 → 10.1 GiB/s    （4.7 倍）
ΔTTFT     138 / 207 / 206 / 147 / 158    ← 无趋势
```

138–207 这个散布，和**单独 page 512 反复跑六次**得到的 147–191（见阶段 09）
是同一个噪声带。**page size 对 TTFT 的影响测不出来。**

这是阶段 08「读时长被调度会合窗口吸收」的第三次独立验证。前两次分别用
改 group size（读变化 4.9 倍）和修设备空转（6.9 倍）来变速，这次用改 page size
（4.8 倍）。三种完全不同的手段，同一个结论。

### 但带宽有个悬崖，在 page 128 和 256 之间

```
page   64:  10.1 GiB/s
page  128:  17.6
page  256:  43.3   ← 悬崖
page  512:  44.0
page 1024:  47.5
```

page ≥ 256 基本持平（43–47 GiB/s）。所以阶段 03/04「page 512 比 page 64 好」的
结论是对的，但**拐点在 256，再往上收益很小**。

**这个悬崖影响的是设备利用率和吞吐，不是单请求 TTFT。** 选 page size 应该按
缓存命中粒度、存储对象数量这些来权衡，TTFT 不构成约束。

## 2. 实验二：扫前缀长度（找拐点）

实验一整个扫描范围内，读都 < 一轮调度会合（约 161 ms），所以没碰到"读开始伤 TTFT"
的拐点。于是固定 page 512，加长命中前缀让读变大。

**事先的预测**（写在跑之前）：

> Δ = 一轮会合 + max(0, 读时长 − 一轮会合)

配置：page 512、后缀 5120、4 个探针、单个发、`max_total_tokens 163840`、
`context_length 139264`。

| 命中前缀 | L2 TTFT | L3 TTFT | **Δ** | L2 queue | L3 queue | 读 span | 带宽 |
|---|---|---|---|---|---|---|---|
| 16384 | 2712 | 2891 | **+179** | 124.2 | 325.8 | 27.3 ms | 46.0 GiB/s |
| 65536 | 5432 | 5698 | **+266** | 134.8 | 515.1 | 84.9 ms | 58.9 GiB/s |

（第三档 `hit 131072` 没跑成，见 §5。）

### 差距确实变大了，但预测的机制是错的

L3 的排队时间可以三段分解，加起来对得很准：

| | 入队 → 读开始 | 读本身 | 读完 → 准入 | 合计 | 实测 L3 queue |
|---|---|---|---|---|---|
| hit 16384 | 145.5 | 27.3 | 151.6 | 324.4 | 325.8 |
| hit 65536 | 202.0 | 84.9 | 226.0 | 512.9 | 515.1 |
| **增量** | **+56.5** | **+57.6** | **+74.4** | | |

**三段全都涨了**，而不是只有"读"那一段。

同时，**一轮会合本身几乎没变**：L2 只等一轮，它的排队时间从 124.2 只涨到 134.8 ms。
所以不是"调度变慢了"。

---

## 3. 为什么说驱动因素不是读速度

把两个实验放在一起，矛盾就出来了：

| | 读 span | **ΔTTFT** |
|---|---|---|
| page 64，前缀 16384 | **125.6 ms** | **138 ms** |
| page 512，前缀 65536 | 84.9 ms | **266 ms** |

**读更慢的那一组，Δ 反而更小。** 读时长单独看不能预测 Δ。

能预测 Δ 的是**前缀长度**。它通过至少两条渠道起作用：

**① 入队 → 读开始：+56.5 ms。** 这一段是"查询存储 + 等调度线程分配 host 内存并提交读"。
前缀从 16384 涨到 65536，要查的 page 从 32 个变成 128 个，要分配的 host 内存从
1.25 GiB 变成 5 GiB。**这两个因素我分不开**：实验一里 page 数量从 16 涨到 256
只让这一段涨了 26 ms（146.5 → 172.0），远小于这里的 56.5 ms，所以光靠 page 数量
解释不了——host 内存分配（可能触发驱逐，且在调度线程上）大概率占了大头，
但我没有单独的埋点。

**② 读完 → 准入：+74.4 ms。** 这一段应该就是"等下一趟调度"。一轮是 135 ms，
而这里涨到 226 ms，说明**有时要等两趟**。为什么前缀变长会更容易多等一趟，
**我没有证据**。§6 会列为未解决项。

---

## 4. 被否掉的预测

我事先押的是"Δ = 一轮会合 + max(0, 读 − 一轮会合)"，即读超过 161 ms 才开始计入。

**这个模型不成立**，两处都不对：

- **读 84.9 ms（远低于 161）时 Δ 已经涨了 87 ms**——不是阈值行为。
- **读 125.6 ms（接近 161）时 Δ 是最低的 138 ms**——顺序都反了。

正确的说法是：**在固定前缀下读速度免费；换前缀长度则另说，而且原因不在读。**

记下这条是因为它比结论本身有用：一个看起来很自然的"读超过窗口才收费"的模型，
被一组交叉对照直接推翻了。

---

## 5. `hit 131072` 没跑成：写回只到 89%

第三档崩在预热阶段：

```
TimeoutError: write-through never reached 193912485888 bytes (last 193192000512)
```

差 720 MB。门槛是预期 KV 的 90%，实际只写回了 **89.2%**（76.6 / 85.9 GB）。

**这大概率是个真问题，不是 bench 门槛设紧了**：前缀 16384 时写回是
「20.00 GiB / 预期 20.00 GiB」，**100% 一分不差**；到 131072 只有 89%。
说明超长前缀下 write-through 有页没被备份到存储。

这是个比例问题，和探针数量无关，所以减少探针重跑还会失败。**未查。**

## 6. 不确定的地方

1. **§3① 的两个原因分不开**：page 数量增加 vs host 内存分配增加，
   都会让"入队 → 读开始"变长，现有埋点区分不了。
2. **§3② 完全没解释**：前缀变长为什么会让"读完 → 准入"从 151.6 涨到 226.0。
3. **拐点只有两个点**，第三个（读 > 161 ms）因为 §5 的问题没拿到。
   所以"读超过一轮会合会怎样"**仍然没有数据**——§4 否掉的是"只有超过才收费"，
   不是"超过了也不收费"。
4. **两个实验的服务端配置不同**（`max_total_tokens` 98304 vs 163840、
   探针数 8 vs 4、是否设 `context_length`），所以 §3 那张跨实验对照表
   只能用来说明"读时长不能单独预测 Δ"，不能拿来做定量比较。
5. **每档单次运行。** 可比噪声带来自阶段 09 的六次重复（147–191 ms）。
6. **绝对 TTFT 不代表生产性能**：沿用单请求基准配置（关闭分块预填充、triton、
   无 CUDA graph）。两臂同配，相对差值可信。

## 7. 怎么复现

```bash
cd /home/lpl/sglang/benchmark/hicache

# 实验一：扫 page size（64/128/256/512/1024）
/home/lpl/sglangtest/.venv/bin/python bench_steady_state_l3_probe.py \
  --server l3_fused --io-threads 8 \
  --page-size 512 --hit-tokens 16384 --suffix-tokens 5120 --probes 8 \
  --max-total-tokens 98304 --hicache-ratio 6.0 \
  --store-root /zion0/kv-aio-bench/<每档独立目录>

# 实验二：扫前缀长度（16384/65536）
/home/lpl/sglangtest/.venv/bin/python bench_steady_state_l3_probe.py \
  --server l3_fused --io-threads 8 \
  --page-size 512 --hit-tokens 65536 --suffix-tokens 5120 --probes 4 \
  --max-total-tokens 163840 --context-length 139264 --hicache-ratio 6.0 \
  --store-root /zion0/kv-aio-bench/<独立目录>
```

**`max_total_tokens` 必须能被 page size 整除**——98304 可以（1024 的 96 倍），
100000 不行。前缀长度实验还需要放开 `context_length`，因为命中前缀 + 后缀
超过了 checkpoint 的 131072。

原始数据：`benchmark/hicache/results/l2l3_fusion/page{64,128,256,512,1024}/`
和 `hit{16384,65536}/`
