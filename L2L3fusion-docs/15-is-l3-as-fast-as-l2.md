# 阶段 15：从 L3 读 KV 到底比从 L2 读慢多少

| | |
|---|---|
| 日期 | 2026-09-23 |
| 模型 | Llama-3.3-70B-Instruct-FP8，TP=2 |
| 存储 | GPFS `/zion0`，O_DIRECT，读路径走 NIXL POSIX |
| 脚本 | `bench_load_sweep.py`（实验一）、`bench_mixed_l2_l3.py`（实验二）、`bench_h2d_vs_storage.py`（实验三） |
| 前一阶段 | [13 并发准入](13-why-all-eight-admit-together.md)、[14 混合命中与 NIXL](14-mixed-l2-l3-and-nixl.md) |

> **要证的命题**：L1+L2+L3 的性能和 L1+L2 差不多，也就是从 L3 读 KV 不比从 L2 读慢。
>
> **结论一**：**在 forward 这一层成立。** 六个可用数据点里五个 L3 更快
> （−26 到 −146 ms），一个持平。
>
> **结论二**：**机制不是"读得快"，而是"读得早"。** 实测 GPFS 39.58 GiB/s
> 比 PCIe 的 52.82 GiB/s **慢 1.33 倍**；L3 的 forward 之所以更短，是因为
> 流水线在准入阶段就把 H2D 提前开始了。
>
> **结论三**：**端到端 TTFT 上不成立。** L3 恒定贵 250–550 ms，
> 这笔钱**全在 queue 上**，和读速度无关。
>
> **结论四**：**挂上 L3 后端本身不要钱**（queue 7.5 → 4.3 ms），
> 但写回让背景吞吐掉了 25%。

---

## 1. 实验一：负载扫描

三条流跑在**同一个服务端**上（L3 后端一直开着），区别只是工作集大小——
这也正是真实场景里 L2 和 L3 的区别：

| 流 | 前缀池 | 为什么会落在那一层 |
|---|---|---|
| `l2` | 15 条循环 | 比设备池（10 条）大所以不是 L1，比 host 池（30 条）小所以留在 L2 |
| `l3` | 60 条循环 | host 池的两倍，转半圈回来必被驱逐 |
| `mixed` | 15 热 + 60 冷交替 | 设计是 50/50 |

负载用**闭环并发**扫，不是固定到达率——闭环不会因为发得比服务得快而让队列发散。
分流**不靠假设靠实测**：每个请求按返回的 tier 归类。

### 结果（均值；并发 1/2/4 来自 `sweep-v2`，8/16 来自 `sweep-v3`）

| 并发 | l2 TTFT | l3 TTFT | **TTFT 差** | **比值** | l2 queue | l3 queue | l2 forward | l3 forward | **forward 差** |
|---|---|---|---|---|---|---|---|---|---|
| 1 | 409.9 | 694.9 | +285.0 | **1.70** | 1.4 | 280.6 | 281.0 | 283.0 | +2.0 |
| 2 | 656.4 | 900.4 | +244.0 | **1.37** | 2.2 | 308.0 | 525.2 | 440.0 | **−85.2** |
| 4 | 1160.6 | 1420.7 | +260.1 | **1.22** | 3.5 | 291.9 | 1023.5 | 997.2 | **−26.3** |
| 8 | 2186.5 | 2563.8 | +377.3 | **1.17** | 6.1 | 495.4 | 2049.3 | 1928.8 | **−120.5** |
| 8（复跑） | 2175.3 | 2544.3 | +369.0 | **1.17** | 5.9 | 495.6 | 2032.3 | 1907.3 | **−125.0** |
| 16 | 3887.4 | 4435.6 | +548.2 | **1.14** | 268.9 | 1579.5 | 2046.4 | 1930.7 | **−115.7** |

并发 8 两次独立运行给出 +377.3 和 +369.0，**可复现**。

### forward：L3 不慢，而且通常更快

五个档里 L3 快 26–125 ms，一个档持平（并发 1，+2.0 ms）。
**从 L3 读 KV 没有让 forward 变长。**

### TTFT：比值收敛，绝对差不收敛

```
比值    1.70 -> 1.37 -> 1.22 -> 1.17 -> 1.14      单调下降
绝对差  +285 -> +244 -> +260 -> +373 -> +548      不收敛
```

差距全在 queue：

```
l2 的 queue    1.4 -> 2.2 -> 3.5 -> 6.0 -> 268.9
l3 的 queue  280.6 -> 308.0 -> 291.9 -> 495.5 -> 1579.5
```

### 一个被证伪的预测

设计这个实验之前我押的是：**负载上来后请求本来就要排队，预取藏在这段等待里
就免费了，差距会收敛到 0。**

**没有兑现。** 并发 16 时 `l2` 确实开始排队了（queue 从 6 涨到 269 ms），
确实进到了我说的那个 regime；但 `l3` 的 queue 是 **1579 ms**，涨得比 `l2` 快得多。

原因和[阶段 13](13-why-all-eight-admit-together.md) 一致：阶段 B（分配 host
内存 + 提交读）在调度线程上**串行**，约 21 ms/请求。并发 16 就是
16 × 21 ≈ 336 ms 的纯串行暂存。**排队时间变长的同时，预取要等的那个调度线程
也变忙了**，所以追不上。

### 并发 32 作废，但挖出一个静默退化

`l3` 流 64 个请求里 **34 个彻底没命中**（全量重算，TTFT 110 秒）。排除了：

| 怀疑对象 | 证据 |
|---|---|
| 存储驱逐 | 目录 251 GiB < 上限 400 GiB |
| 流水线超时 | `exceeded its storage timeout` 0 次 |
| 跨 rank 失败 | `failed on a peer rank` 0 次 |
| retract / preempt | 各 0 次 |
| IO 失败 | 794 次流式准入、794 次流式读，全部成功 |

真实原因是 **host 暂存不够**：host 池 492032 token，而 32 个并发的暂存需求是
32 × 16384 = **524288 token**，比整个池子还大。此时走的是这条路径：

```python
# unified_radix_cache.py
if host_indices is None:
    self.revoke_pending_prefetch(req_id)   # 一行日志都不打
    return True
```

`revoke_pending_prefetch` **完全静默**——没有日志、没有指标。所以 L3 路径在
host 暂存不足时会**悄悄退化成全量重算**，线上根本看不出来。这是个独立于本实验
的观测性缺口，见 §5。

## 2. 实验二：把两段代价分开

实验一里三条流都开着 L3 后端，所以"挂上后端"这件事本身的代价被吃进了基线。
这个实验用三个臂把它拆出来，每个臂各起一次服务端、各用独立的 store。

| 臂 | 后端 | 探针命中 | queue | forward | 背景 tok/s | 批次形状 |
|---|---|---|---|---|---|---|
| `l2_no_l3` | 无 | 全 L2 | **7.5** | 2082.2 | **59.2** | 1 批 × 8 |
| `l2_with_l3` | NIXL | 全 L2 | **4.3** | 1046.0 | **44.2** | 2 批 × 4 ⚠️ |
| `l3_all` | NIXL | 全 L3 | **514.3** | 1935.8 | **43.3** | 1 批 × 8 |

**① 挂上 L3 后端本身不花排队时间。** 7.5 → 4.3 ms，在噪声里。

**② 代价全在"从 L3 读"这一步。** 4.3 → 514.3 ms。

**③ 背景吞吐降的 25% 几乎全是写回，不是预取。** 59.2 → 44.2 是开后端（写回）造成的，
44.2 → 43.3 才是真正读 L3 的代价，只有 2%。
这解决了[阶段 14 §7](14-mixed-l2-l3-and-nixl.md) 里那个当时分不开的混淆项。

**④ `l2_no_l3` 对 `l3_all` 是干净对照**——批次形状完全相同
（`#new-seq: 8, #cached-token: 131072, #running-req: 6`）：

```
TTFT    +362.0 ms
queue   +506.8 ms
forward -146.4 ms   <- L3 更快
```

> ⚠️ **`l2_with_l3` 的 TTFT 和 forward 不可比**：它的 8 个探针被拆成了两批 4 个
> （`token usage 0.45` vs 另外两臂的 `0.86`），前 4 个 TTFT ~1100、后 4 个 ~2115。
> 为什么开了后端反而一批装不下 8 个，**没查**。它的 queue 和背景吞吐仍然可用。

## 3. 实验三：PCIe 对 GPFS

```
一条 16384-token 前缀的 KV = 2.50 GiB
GPU: NVIDIA RTX PRO 5000 72GB Blackwell

内存           块大小MiB     块数      耗时ms    GiB/s
pinned       2560.0      1     47.33    52.82
pinned        256.0     10     47.33    52.82
pageable     2560.0      1     54.35    45.99
pageable      256.0     10     54.93    45.51
```

| | 带宽 |
|---|---|
| L2 → L1（PCIe，pinned 上界） | **52.82 GiB/s** |
| L3 → L2（GPFS，实测读报告） | **39.58 GiB/s** |
| 比值 | **0.75x** |

### 这推翻了我自己之前的说法

我在设计实验时说过"GPFS 比 PCIe 快 4 倍多"，依据是从 L2 命中的 forward 反推出
H2D 约 9 GiB/s。**那个反推无效**——forward 里还含计算，不能当作纯搬运。
实测 GPFS 比 PCIe **慢** 1.33 倍。

### 所以结论一的解释要改

L3 的 forward 更短，**不是因为读得快，是因为读得早**：流水线在准入阶段就
逐组发起了 L2→L1 的 H2D，forward 开始时已经搬了一部分；L2 命中走的是 forward
期间的 `load_back`。**是重叠，不是速度。**

顺带两个观察：块大小 2560 MiB 和 256 MiB 的带宽**完全一样**（47.33 ms），
说明 H2D 在这个量级上不受分块粒度影响；pageable 只比 pinned 慢 13%。

## 4. 三个实验合起来

| 命题 | 结论 |
|---|---|
| 从 L3 读 KV 不比从 L2 慢（forward） | **成立**，六个点里五个更快 |
| 机制是 GPFS 比 PCIe 快 | **不成立**，GPFS 慢 1.33 倍；靠的是流水线重叠 |
| 挂上 L3 后端本身有延迟代价 | **不成立**，queue 7.5 → 4.3 ms |
| 挂上 L3 后端有吞吐代价 | **成立**，背景吞吐 −25%，几乎全是写回 |
| 端到端 TTFT 持平 | **不成立**，恒定贵 250–550 ms |
| 高负载下这个差距会收敛到 0 | **不成立**，比值收敛到 1.14，绝对差反而涨 |

**那 250–550 ms 全部是调度线程上的串行工作**（阶段 B 约 21 ms/请求），
和读速度、和存储后端都无关——阶段 13、14、15 三次独立实验指向同一处。
要让端到端 TTFT 持平，要动的是**把阶段 B 和 `init_load_back` 从调度线程上挪走**，
不是换更快的存储。

## 5. 不确定的地方 / 待办

1. **`revoke_pending_prefetch` 静默退化**（§1）。host 暂存不足时请求变成全量重算，
   无日志无指标。这是个独立的可提 issue。
2. **`bench_load_sweep.py` 的报警文案是错的**：它把 miss 归因成"存储上限太小"，
   实际是 host 暂存不足。要改。
3. **`l2` 流有 L1 污染**：热池 15 条对设备池 10 条，余量太小。
   实测 L1 占比：并发 1/2/4 为 0%，并发 8 为 17–25%，16 为 19%，32 为 12%。
   L1 命中比 L2 快，所以**基线被拉快了，真实差距比表里的略小**。
4. **`mixed` 流没做成 50/50**：`sweep-v2` 全退化成 L3，`sweep-v3` 并发 16 时是
   14 L2 / 50 L3。热池 15 + 冷池工作集刚好把 30 条的 host 池填满，余量为零，
   背景请求的 KV 一挤就把热的顶出去。这一列没有信息量。
5. **`l2_with_l3` 一批装不下 8 个探针，没查**（§2）。
6. **每个数据点单次运行**，只有并发 8 复跑过一次。
7. **实验三是纯搬运的上界**，不是 hicache 在负载下的实际 H2D 速率。
