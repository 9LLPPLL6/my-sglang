# L3 相比 L2 到底贵在哪 —— 汇报材料

2026-09-23 · Llama-3.3-70B-Instruct-FP8，TP=2 · GPFS `/zion0`，O_DIRECT

---

## 一句话结论

**从 L3 读 KV 不比从 L2 慢，磁盘只值 17 ms。**
L3 多出来的时间几乎全部是**调度线程上的串行 CPU 工作**，和存储快慢无关。

| 场景 | L3 比 L2 多花 | 其中磁盘 | 其中代码路径 | 其中调度排队 |
|---|---|---|---|---|
| 单请求、无背景 | **62 ms** | 17 | 46 | ~0 |
| 有背景、并发 8 | **521 ms** | ~32 | ~19 | **~470** |

# 怎么读这份报告

## 三个时间指标

一个请求的生命周期被服务端切成两段，报告里始终分开报，不合并：

```
客户端发出
   │
   ├── 入队 ────────────────────────┐
   │                                │  queue      排队：等调度线程把它编进一个批次
   ├── 进入 prefill 批次 ───────────┘
   │                                │  forward    前向：真正跑模型，含把 KV 搬进显存
   ├── 第一个 token 吐出 ───────────┘
   │
  TTFT = queue + forward + 客户端往返
```

- **TTFT**：客户端侧测的，从发出请求到收到第一个 token
- **queue**：服务端侧埋点，`forward_entry_time − wait_queue_entry_time`
- **forward**：服务端侧埋点，准入到完成

**为什么要分开看**：L3 的代价几乎全在 queue 上，forward 反而更快。
只看 TTFT 会把这两个相反的效应抵消掉，看不出问题在哪。

**forward 强烈依赖批次里有几个请求**（基本成正比）。所以比较 forward 时
必须确认两边的批次形状相同，否则数字没有意义 —— 报告里凡是比 forward 的地方
都标注了批次形状。

## 分层的判定

每个请求返回时服务端会报它的前缀从哪来，报告里按这个**实测**分类，不按设计假设：

| 归类 | 判据 |
|---|---|
| L1 | `device` 最大，前缀还在显存里 |
| L2 | `host` 最大，从内存搬进显存 |
| L3 | `storage` 最大，从盘上读 |
| **miss** | `cached = 0`，哪一层都没有，**全量重算** |

miss 单独一类很重要：一次全量重算的 forward 可能比 L1 命中还长，
早期版本把 miss 误判成 L1，导致一整轮数据看着像"L1 命中但很慢"。

## 所有数字都是均值

报告里**没有任何中位数**。每处都标了样本量 n。
离散度大到均值不能代表分布的地方，会单独标注（目前只有实验一并发 16 那一档）。

## 怎么让请求落在指定的层

| 要它命中 | 做法 |
|---|---|
| L1（设备） | 刚跑过，还在 HBM 里 |
| **L2（host）** | 预热后用 `evict_device` 灌填充数据把它挤出 HBM；host 池是设备池的 6 倍，副本留在 L2 |
| **L3（存储）** | `flush_cache` 清空 L1 和 L2（**存储上的文件不动**），再把页缓存打冷 |

第三部分实验一不用上面的办法，改用**工作集大小**区分——15 条循环（比 host 池小）
必然命中 L2，60 条循环（host 池两倍）转半圈回来必被驱逐，只能走 L3。
这更接近真实场景，而且**分流是实测的**：每个请求按返回的层归类，报表给出实际命中数。

# 第一部分：单请求、无背景 —— 用"假 IO"把磁盘摘出去

## 怎么做的

写一个补丁，让**最内层的 IO 直接返回**：`LinuxAioContext._submit` 不下发
`io_submit` 系统调用，直接把请求登记成已完成。

**除了内核那一步，其他全部照常执行**——仲裁器、队列深度、分片、extent 状态机、
跨 rank 共识、准入门控、层门、H2D 一个不少。

这样三个臂放在一起，就能把"磁盘"和"代码路径"分开：

| 臂 | 走 L3 代码路径 | 真的读盘 |
|---|---|---|
| L2 | 否 | 否 |
| L3 假 IO | **是** | **否** |
| L3 真 IO | 是 | 是 |

> 补丁不进仓库，只在做实验时打上：`benchmark/hicache/fake_storage_io.patch`

## 样本量与离散度

每臂 **8 个探针**，逐个发（不并发）。离散度很小，均值可代表分布：

| 臂 | n | queue 均值 | 标准差 | forward 均值 | 标准差 |
|---|---|---|---|---|---|
| L2 | 8 | 1.6 | 0.1 | 283.3 | 4.7 |
| L3 假 IO | 8 | 47.5 | 4.9 | 282.8 | 1.1 |
| L3 真 IO | 8 | 64.7 | 7.9 | 282.8 | 0.8 |

## 时刻表（距离请求入队的毫秒，8 个探针均值）

下表每一行是一个事件在**请求入队之后第几毫秒**发生的，不是耗时。
相邻两行相减才是耗时。

| 时刻 | L2 | **L3 假 IO** | **L3 真 IO** |
|---|---|---|---|
| ① 第 0 组提交 | — | 6.7 | 6.9 |
| ② 读开始 | — | 7.0 | 7.0 |
| ③ 其余 9 组提交 | — | 14.3 | 11.8 |
| ④ **第 0 组落地** | — | **14.7** | **26.6** |
| ⑤ 流水线宣告可准入 | — | 14.7 | 26.6 |
| ⑥ 全部 10 组读完 | — | 17.7 | 41.9 |
| ⑦ **请求被准入** | **1.6** | **47.5** | **64.7** |
| ⑧ 请求完成 | 284.8 | 330.3 | 347.5 |

> **④ 的口径**：第 0 组落地的时刻是由调度线程轮询时盖章的，所以它是
> "第 0 组真正读完"的**上界**。这一档无背景请求、调度线程空转，
> 真 IO 臂实测轮询了 15.1 次、假 IO 臂 1.0 次，轮询足够密，
> 所以这个上界很接近真值。**并发场景下这个字段不能这么用**（见第二部分）。

## 三个结论

| | L2 | 假 IO | 真 IO |
|---|---|---|---|
| TTFT 均值 | 291.5 | 336.5 | 353.8 |
| queue 均值 | 1.6 | 47.5 | 64.7 |
| **forward 均值** | **283.3** | **282.8** | **282.8** |
| 读盘 | 0 | **0** | 20 GB |

**① forward 三档完全相同 —— 差异 100% 落在 queue 里。**
从 L3 读 KV 一点没有拖慢计算。

**② 磁盘只值 17 ms。** 假 IO 到真 IO，准入时刻从 47.5 变成 64.7。
所有关于"把读做快"的优化，天花板就是这 17 ms。

**③ 代码路径值 46 ms。** L2 到假 IO，准入时刻从 1.6 变成 47.5。
这才是当时的大头——而且它后来被修掉了一半以上（见下）。

## 顺带发现并修掉的一个同步

准入时有一行代码把两个 CUDA 张量做 `torch.equal` 比对，**强制整卡同步**，
在 forward 还没开始时就把调度线程钉在 GPU 上等 23–45 ms。

改成让树的插入直接返回它做了什么，不再重新匹配一遍来反推：

| | L2 queue | L3 queue | **Δ** |
|---|---|---|---|
| 改前 | 1.6 | 47.5 | **45.9** |
| **改后** | 1.6 | **20.8** | **19.2** |

**−26.7 ms，降 58%。** L2 基线和两臂的 forward 都没动。

剩下的 19 ms 分布在查存储、分配 host、建计划、提交 640 个 extent、仲裁器、
状态机、共识、准入这一整串上，**没有单独一项占主导**。

# 第二部分：并发 8 —— 开销在时间轴上的位置

> **说明**：并发场景**没有跑假 IO**。这里用的是直接埋点（扫描计数器 + 每笔事务的
> 阶段时刻），比推算更硬。

配置：8 个探针并发发出、6 路背景解码、命中前缀 16384 token。

实测 **L2 queue 5.1 ms，L3 queue 525.8 ms**。下面拆这 526 ms。

## 时序图

```
时刻        调度线程                              预取线程      IO 线程 x8
==============================================================================
 t1  +0ms   收到 8 个探针
            +- 8 个一起入队
            +- 查 L1/L2 -> 全部落空
            +- 发起 8 个存储查询 ---------------->  查 8x32 个 page
            +- 扫描等待队列：8 个全部跳过
            |    （读还没提交，流水线里还没有事务）
            |    实测这一趟只花 1.2 ms
            +- 建批次（只有 6 个背景请求）-> 跑 forward
      <== L2 探针就是在这一趟被准入的（queue 5.1ms）==
                                          查完，8 个结果入队
------------------------------------------------------------------------------
 t2 +142ms  排空存储命中队列
            +- 请求0：分配 host 1.25GiB，提交读 ------->  开始读 0
     +154ms +- 请求1 ...                              ->  开始读 1
     +170ms +- 请求2 ...                                  整读0 完 +189
       ...                                                整读1 完 +215
     +294ms +- 请求7：提交读                               ...
            ^ 这 152ms 全在调度线程上串行，19ms/请求

     +302ms 扫描等待队列
            +- 请求0 的检查 -> 推进全部 8 笔事务
            |    事务0..6 第0组已就绪 -> 依次宣布准入
            |    事务7 还没好，下一次推进时（+328）才就绪
            +- 请求0..7：树匹配 + init_load_back
            |    实测 检查 63ms + init_load_back 160ms = 224ms，28ms/请求
     +526ms +- 建批次 -> 请求正式进入 prefill
      <== L3 探针到这里才被准入 ==
            跑 forward（探针自己的 prefill）
==============================================================================
```

## 526 ms 花在哪（墙钟）

```
  0 -> 142    142 ms   等调度线程下一趟（存储查询在预取线程上并行跑完了）
142 -> 294    152 ms   分配 host 内存 + 提交读，串行，19 ms/请求
294 -> 302      8 ms   扫描开始
302 -> 526    224 ms   扫描循环遍历 8 笔事务，28 ms/请求
                       +- init_load_back        160 ms
                       +- 检查预取进度            63 ms
              ------
               526 ms
```

**读盘整个藏在里面，一毫秒都没暴露。**

读的耗时是 **53.0 ms**（均值，范围 26.3–125.1，带宽 28.8 GiB/s）。这个数的口径要说清楚：

- **每笔事务、每个 rank 各一条日志**，16 条取均值（8 笔事务 x 2 个 rank），**不是 8 个请求相加**
- 量的是**整条前缀 10 个组**（32 个 page、640 个 extent、1.25 GiB/卡），**不是第 0 组**
- 8 笔读是**并发**的，所以墙钟上它们互相重叠，不是 8 x 53 ms

**第 0 组单独要多久，这一轮测不出来**——`g0_local_done` 是调度线程来看时才盖的章，
量的是"提交完到调度线程回头看"，不是读耗时。唯一直接观察到第 0 组读时间的是
第一部分（无背景、单请求）：读从 7.0 开始、第 0 组 26.6 落地，**约 19.6 ms**；
对照假 IO 的 14.7，其中**磁盘约占 12 ms**。

## 这一轮的 forward 不能用来比 L2 和 L3

有人会照着上面的表问"那 forward 呢"。**这一轮比不了**，因为两个臂的批次形状不同：

| 臂 | 批次 | forward |
|---|---|---|
| L2 | 拆成两批：3 个（cached 49152）+ 5 个（cached 81920） | 800 / 1269 |
| L3 | 一批 8 个（cached 131072） | 1908 |

forward 基本正比于批内请求数（每个请求摊 239–267 ms），所以 1093 对 1908
这个差是批次大小造成的，不是 L2 与 L3 的差别。

**批次形状钉死了的干净对照在别处**：

| 来源 | 批次形状 | L2 forward | L3 forward | 差 |
|---|---|---|---|---|
| 第三部分实验二 | 1 批 x 8 个，cached 131072 | 2082.2 | 1935.8 | **−146.4** |
| 第三部分实验一 并发 8 | 闭环流，形状未钉死 | 2049.3 / 2032.3 | 1928.8 / 1907.3 | −120.5 / −125.0 |

L2 臂为什么会被拆成两批而 L3 臂是完整一批，**没查**
（实验二的 `l2_with_l3` 也出现过同样现象）。

## 三个被数据否掉的猜测

做这个实验前我列了三个可能原因，**全错**：

| 猜测 | 埋点结果 |
|---|---|
| 批次满了，扫描被短路 | 每轮都遍历了全部 8 个，从来没有 break |
| 容量不够，请求被拒 | 同上，`stop=ran-to-end` |
| 调度器提前返回，压根没扫 | 两趟扫描都打印了日志 |

真相是：**第一趟时读还没被提交**（存储查询没回来），第二趟时 8 个一起就绪。
不是调度器漏看了谁。

## 一个反向佐证

第 8 笔事务在 **+328ms 就被宣布准入**，而它整条前缀读到 **+421ms** 才结束，
**提前了 93 ms**。说明"第 0 组落地就准入"这个设计是在正常工作的，
问题不在准入条件上。

# 第三部分：L3 到底比 L2 慢多少（三个新实验）

## 实验一：负载扫描

**L3 的读走 NIXL POSIX**（`--server l3_nixl`，日志可见 `NixlIoContext: plugin=POSIX`）。
三条流跑在**同一个服务端**上，L3 后端一直开着——所以"开不开后端"这个变量被排除了，
剩下的差就是"从哪读"。三条流的区别是**工作集大小**，不是开关：

| 流 | 请求从哪组前缀里取 | 于是 |
|---|---|---|
| `l2` | 只取那 **15 条**，循环用（比 host 池的 30 条少） | 一直在内存里，命中 L2 |
| `l3` | 只取那 **60 条**，循环用（是 30 条的两倍） | 轮到时早被挤出内存，走 L3 |
| `mixed` | 两组交替取 | 设计是一半一半，但**没做成**，见下 |

之所以要造两组而不是一组：**没法用同一组前缀既测 L2 又测 L3**——
同一条前缀从盘上读过一次就进内存了，第二次再用它就变成 L2 命中。

> **`mixed` 流没做成，所以下面的结果表里没有它。** 设计是 50/50，实测六个档里
> 五个档命中内存的只有 0 到 1 个请求，**它实际上就是 `l3` 流**（TTFT 也几乎重合：
> 2560 vs 2564、2536 vs 2544）。原因是 host 池只装得下 30 条、余量为零——
> 交替发请求时每个走盘的请求都要占掉空间，再加上 6 路背景请求自己的 KV，
> 那 15 条很快被顶出去。只有并发 16 那一档部分起作用（64 个里 14 个命中内存）。
> **下表的 `l3` 列是纯 `l3` 流的数，没有和 mixed 做任何合并或平均。**

**为什么不用前面那套 `flush_cache` + `evict_device`**：那套是给单次突发用的。
连续发请求时，同一条前缀第一次从 L3 读完就进 L2 了，后面全变成 L2 命中，
`l3` 流会自己退化掉。用工作集大小区分才能**持续**从 L3 读，也更接近真实场景。

**负载用闭环并发扫**（N 个客户端背靠背发，N = 1/2/4/8/16），不用固定到达率——
闭环不会因为发得比服务得快而让队列发散。

流程：

```
1. 预热 75 条前缀（15 热 + 60 冷）全部写进 L3        约 187 GiB
2. 启动 6 路背景解码请求，全程开着
3. 每个并发档 x 每条流：
     a. warmup 请求（不计入统计），把工作集做到稳态
        l2 循环热池一遍(15 个)，l3 循环冷池前半(30 个)
     b. 64 个请求，记录 TTFT / queue / forward / tier
4. 每个请求按返回的 tier 归类 —— 分流是实测的，不是假设的
```

报表里 `实测L1/L2/L3/miss` 那一列就是校验：`l2` 流必须是 `0/N/0/0`，
`l3` 流必须是 `0/0/N/0`，否则该档作废（并发 32 就是这样被判掉的）。

| 并发 | l2 TTFT | l3 TTFT | **差** | **比值** | l2 queue | l3 queue | l2 forward | l3 forward | **forward 差** |
|---|---|---|---|---|---|---|---|---|---|
| 1 | 409.9 | 694.9 | +285 | **1.70** | 1.4 | 280.6 | 281.0 | 283.0 | +2.0 |
| 2 | 656.4 | 900.4 | +244 | **1.37** | 2.2 | 308.0 | 525.2 | 440.0 | **−85.2** |
| 4 | 1160.6 | 1420.7 | +260 | **1.22** | 3.5 | 291.9 | 1023.5 | 997.2 | **−26.3** |
| 8 | 2186.5 | 2563.8 | +377 | **1.17** | 6.1 | 495.4 | 2049.3 | 1928.8 | **−120.5** |
| 8 复跑 | 2175.3 | 2544.3 | +369 | **1.17** | 5.9 | 495.6 | 2032.3 | 1907.3 | **−125.0** |
| 16 | 3887.4 | 4435.6 | +548 | **1.14** | 268.9 | 1579.5 | 2046.4 | 1930.7 | **−115.7** |

表头说明：**差** = l3 TTFT − l2 TTFT；**比值** = l3 TTFT ÷ l2 TTFT。
每档 n=24（并发 1/2/4）或 n=64（并发 8/16），全部是均值。

**forward：六个点里五个 L3 更快（快 26–125 ms），一个持平。**
从 L3 读 KV 没有让计算变慢。

**TTFT：比值从 1.70 收敛到 1.14，但绝对差不收敛（250–550 ms），全在 queue 上。**

> **比值下降不是好消息，是分母效应。** 基线 l2 的 TTFT 从 409.9 涨到 3887.4
> （9.5 倍），而 L3 多花的毫秒只从 285 涨到 548（1.9 倍）。高并发下所有请求
> 本来就慢，多这 500 ms 占比自然小，但**用户感受到的是那 500 ms 不是那 14%**。
> 报"L3 贵多少"要用绝对差；比值那一列的唯一作用是说明**没有收敛到 0**。

### 离散度：并发 16 那一档的均值不可信

| 档 | queue 均值 | 标准差 | 最小 | 最大 |
|---|---|---|---|---|
| 并发 1 l2 / l3 | 1.4 / 280.6 | 0.1 / 4.0 | 1.3 / 268.9 | 1.6 / 286.7 |
| 并发 2 l2 / l3 | 2.2 / 308.0 | 0.2 / **93.5** | 1.9 / 167.3 | 2.7 / 463.3 |
| 并发 4 l2 / l3 | 3.5 / 291.9 | 0.2 / 5.0 | 3.1 / 285.3 | 3.8 / 298.7 |
| 并发 8 l2 / l3 | 5.9 / 495.6 | 0.4 / 10.8 | 5.0 / 480.2 | 6.7 / 509.3 |
| **并发 16 l2** | **268.9** | **692.4** | **6.2** | **2101.4** |
| **并发 16 l3** | **1579.5** | **1045.3** | 528.8 | 2685.4 |

**并发 16 的 l2 流是双峰分布**：标准差是均值的 2.6 倍，一部分请求根本没排队
（6 ms，和并发 8 一样），一部分等了 2 秒。均值 268.9 落在两个峰中间，
**没有任何一个请求是这个值**。所以：

- 并发 16 那一行的 **+548 ms 不能当精确值引用**，只能看方向
- 我之前说"并发 16 时 l2 开始排队了"，更准确的说法是**一部分请求进了排队状态，一部分没进**
- 但**两条流的分布几乎不重叠**（l3 最少也要等 528.8 ms），L3 更贵这个方向是确定的

并发 2 的 l3 也偏散（标准差 93.5，范围 167–463，n=24），可能是某几个请求
赶上了不同的调度时机，没细查。并发 1/4/8 三档离散度都很小，均值可信。

## 实验二：把"挂上后端"和"从 L3 读"分开

**和实验一的做法完全不同**：实验一是三条流共用一个服务端、闭环持续发请求；
这里是**每个臂各起一次服务端**，每个臂只发**一次** 8 个并发探针。
L3 的读同样走 NIXL POSIX。

设计意图是每次只变一个东西：

```
l2_no_l3  ->  l2_with_l3    只变"后端开不开"，请求都命中内存
l2_with_l3 ->  l3_all       只变"从哪读"，后端都开着
```

### 每个臂的流程

```
1. 启动服务端
2. flush_cache 清空所有缓存
3. 预热 8 条前缀（各 16384 token）—— 这一步顺带把它们写进盘
4. 等写回完成（实测正好 20.00 GiB）      <- 不开后端的臂跳过 3 的写盘和这一步

5. 摆位置（三个臂唯一的差别就在这一步）：
   l2_no_l3    什么都不做，本来就只在内存里
   l2_with_l3  再 flush_cache 一次清掉内存副本（盘上的文件不动），
               打冷页缓存，然后把 8 条全部重新读回内存
   l3_all      同上，但一条都不读回 —— 于是它们只在盘上

6. evict_device：灌填充数据把这 8 条挤出显存
   （内存池是显存池的 6 倍，所以内存副本留得住）
7. 启动 6 路背景解码请求，等 8 秒
8. 8 个探针一次性并发发出
9. 记 TTFT 和分层；用请求 id 去日志里把 queue 和 forward 对上
10. 逐个探针校验分层，关服务端，下一个臂
```

第 5 步能成立的前提是 **`flush_cache` 只清显存和内存，不动盘上的文件**。

三个臂，每个臂各起一次服务端，n=8：

| 臂 | 后端 | 探针命中 | queue | 背景吞吐 tok/s |
|---|---|---|---|---|
| 不开 L3 | 无 | 全 L2 | **7.5** | **59.2** |
| 开 L3，全命中 L2 | NIXL | 全 L2 | **4.3** | **44.2** |
| 开 L3，全走 L3 | NIXL | 全 L3 | **514.3** | **43.3** |

**① 挂上 L3 后端本身不花排队时间**（7.5 → 4.3 ms，在噪声里）。

**② 延迟代价全在"从 L3 读"这一步**（4.3 → 514.3 ms）。

**③ 吞吐代价则相反 —— 背景吞吐降的 25% 几乎全是写回**
（59.2 → 44.2 是开后端造成的，真正读 L3 只再降 2%）。

**④ 不开 L3 对全走 L3 是干净对照**：两者都是 1 批 x 8 个、cached 131072、
背景 6 路，批次形状完全相同，所以 forward 可比。
TTFT +362 ms，queue +507 ms，**forward −146 ms（L3 更快）**。

### 这个实验的两个已知缺陷

**① `l2_with_l3` 的 TTFT 和 forward 不可比。** 它的 8 个探针被拆成了两批 4 个
（`token usage 0.45`，另外两臂是 `0.86`），前 4 个 TTFT ~1100、后 4 个 ~2115。
为什么开了后端反而一批装不下 8 个，**没查**。
它的 **queue（4.3 ms）和背景吞吐（44.2）仍然可用**，上面 ① 和 ③ 两条结论就建立在这两个数上。

**② 踩过一个坑，已修。** `l2_with_l3` 和 `l3_all` 用的是同一种服务端，
一开始也就共用同一个存储目录；而三个臂用的是**同一组前缀**，所以第三个臂预热时
页早就在盘上，写回增长为 0，而等待写回是按**增长**判定的 —— 死等超时崩掉。
现在每个臂用 `<存储根目录>/<臂名>/` 各自独立的目录。
（作废的那一轮是 `arms-v1`，有效数据是 `arms-v2`。）

## 实验三：GPFS 对 PCIe 的带宽

| | 带宽 |
|---|---|
| L2 → L1（PCIe，pinned 上界） | **52.82 GiB/s** |
| L3 → L2（GPFS，实测） | **39.58 GiB/s** |
| 比值 | **0.75x** |

**GPFS 比 PCIe 慢 1.33 倍。**

> **这两个数的口径不对等，但方向可信。**
> PCIe 那个是**纯搬运的上界**：一段 pinned 内存直接 `copy_` 到显存，
> 不经过 hicache 的任何代码，每档重复 5 次取均值（丢掉第一次预热）。
> GPFS 那个是**真实负载下**的读，含打开文件、仲裁、分片、640 个 extent 的提交。
> 也就是说真实的 PCIe 速率只会比 52.82 更低、GPFS 只会比 39.58 更高，
> 所以"GPFS 不比 PCIe 快"这个结论是保守的。

所以"L3 的 forward 更快"**不是因为读得快，是因为读得早**——流水线在准入阶段
就逐组发起了 H2D，forward 开始时已经搬了一部分。**是重叠，不是速度。**

# 汇总：命题核对

| 命题 | 结论 |
|---|---|
| 从 L3 读 KV 不比从 L2 慢（forward 层面） | **成立**，六个点里五个更快 |
| 机制是 GPFS 比 PCIe 快 | **不成立**，GPFS 慢 1.33 倍，靠的是流水线重叠 |
| 挂上 L3 后端有延迟代价 | **不成立**，queue 7.5 → 4.3 ms |
| 挂上 L3 后端有吞吐代价 | **成立**，背景吞吐 −25%，几乎全是写回 |
| 端到端 TTFT 持平 | **不成立**，恒定贵 250–550 ms |
| 高负载下这个差距会收敛到 0 | **不成立**，比值收敛到 1.14，绝对差反而涨 |

# 下一步该动哪里

那 250–550 ms 全部是调度线程上的串行工作，**和读速度、和换什么存储后端都无关**。
三个阶段的实验独立指向同一处：

| 入口 | 量级 | 说明 |
|---|---|---|
| **阶段 B 从调度线程挪走** | 152 ms | 分配 host 内存 + 提交读，19 ms/请求。它不碰 GPU 也不碰批次状态，没有理由占着调度线程 |
| **`init_load_back` 瘦身** | 160 ms | 20 ms/请求。之前修掉过一次 GPU 同步（−26.7 ms），剩下的还没拆过是设备分配、树插入还是 H2D 会话 |
| 把读做更快 | ≤ 17 ms | **天花板就这么高**，不值得再投入 |

# 已知的坑与不确定的地方

1. **并发场景没有跑假 IO。** 第二部分用的是直接埋点，不是三臂对照。
2. **`l2` 流有 L1 污染**：并发 8 时 17–25% 的请求命中了 L1（比 L2 快），
   所以基线被拉快了，**真实差距比表里的略小**。
3. **并发 32 那一档作废**：host 池装不下 32 个并发的暂存（需要 524288 token，
   池子只有 492032），预取被**静默撤销**，请求退化成全量重算。
   `revoke_pending_prefetch` 不打任何日志也没有指标 —— 这是个独立的观测性缺口，
   线上出了根本看不出来。
4. **每个数据点单次运行**，只有并发 8 复跑过一次（+377 / +369，可复现）。
5. **绝对 TTFT 不代表生产性能**：沿用基准配置（关闭分块预填充、无 CUDA graph）。
   两臂同配，相对差值可信。
