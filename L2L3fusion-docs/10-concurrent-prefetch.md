# 阶段 10：并发预取会让 TTFT 差多少

| | |
|---|---|
| 日期 | 2026-09-20 |
| 模型 | Llama-3.3-70B-Instruct-FP8，TP=2 |
| 存储 | GPFS `/zion0`，O_DIRECT |
| 脚本 | `benchmark/hicache/bench_steady_state_l3_probe.py --probe-concurrency N` |
| 前一阶段 | [09 汇报文档](09-ttft-attribution-report.md)、[08 归因](08-where-the-180ms-actually-goes.md) |

> **问题**：之前所有实验都是一个一个发探针，L3 比 L2 慢约 180 ms。
> 如果多个请求同时来、同时要从 L3 预取，会不会更差？
>
> **答案**：会。默认配置下从 180 ms 涨到 **249 ms**；
> 如果把"允许几笔同时走流式"从 1 放开到 8，涨到 **561 ms**。

---

## 1. 结果

| 场景 | Δ TTFT p50 | Δ max | 倍数 |
|---|---|---|---|
| 单个探针（基线） | +180 ms | — | 1.07× |
| **8 并发，流式槽位 = 1（当前默认）** | **+249 ms** | +248 ms | 1.11× |
| 4 并发，流式槽位 = 4 | +303 ms | +321 ms | 1.26× |
| **8 并发，流式槽位 = 8** | **+561 ms** | +560 ms | 1.26× |

两个要点：

- **并发确实让差距变大**：180 → 249 ms。
- **放开流式槽位让差距再翻一倍多**：249 → 561 ms。默认值 1 不应该改。

一个好消息：**尾部没有爆炸**。Δmax 和 Δp50 几乎相等（248/321/560 对 249/303/561），
说明整个分布是平移，不是少数请求被拖垮。
阶段 06 当时测并发流式，max 涨了 **6.2 秒**——那个问题已经不存在了
（原因见 §5）。

---

## 2. 实验怎么做的

和之前的稳态实验一样，只多了一个旋钮。

**两个旋钮要分清**：

| 旋钮 | 含义 |
|---|---|
| `--probe-concurrency N` | 客户端同时发 N 个探针 → N 笔预取同时在途 |
| `--max-concurrent-streams M` | 服务端允许 M 笔同时走流式，**超出的回退到阻塞整块读** |

**流程**（L2 / L3 两个臂在同一个服务进程内先后跑，配置完全相同）：

```
① 预热   8 条各 16384 token 的前缀写进存储（共 20 GiB）
② 造场景  L2 臂：只把前缀挤出 HBM，host 里还有
          L3 臂：清空 HBM + host，只剩存储里那份
③ 背景   6 个长生成请求持续 decode，让 GPU 一直忙着
④ 探针   8 个，每波 N 个同时发
⑤ 校验   每个探针的命中层级 + 进程读盘计数器（L2 臂必须是 0）
```

**一个必须说的修正**：第一轮实验用的后缀是 5120 token，结果 8 个探针同时到达时，
GPU 要预填充 8 × 5120 = 41k 个新 token，TTFT 飙到 **18 秒**——探针变成了预填充洪水，
预取的代价被淹没了。后来把后缀降到 **512**，TTFT 回落到 1–2 秒，
预取的量（16384 前缀）一字未变。**上面的结果全部来自修正后的那一组。**

---

## 3. 为什么并发会让 TTFT 变差

先回顾单请求时的结论（阶段 08）：那 180 ms **不是存储慢**，
而是准入要多等一趟调度线程的会合——读只要 25 ms，但"读完了"这件事
只有调度线程能发现，它一轮才来一次。

并发之后，在这个基础上多了两层压力：

**① 每笔读变慢了。** 单笔独占设备时读 25 ms；8 笔同时抢，每笔变成 19–36 ms
（阻塞读 19.4 ms，流式 36 ms）。设备带宽是共享的。

**② 调度线程每轮要干的活变多了。** 8 笔预取意味着每轮要排空 8 个命中、
做 8 次内存分配、检查 8 次进度。这些全部串在同一个调度线程上。

不过要老实说：**+180 → +249 这 69 ms，我没能精确拆到上面哪一条。**
单笔读的耗时并没有暴涨（19–36 ms，和单笔的 25 ms 同一量级），
所以不像是纯粹的带宽争用。§7 会说明为什么这次拆不出来。

---

## 4. 为什么阻塞读反而比流式读好

这是本阶段最反直觉的一点。同样是 8 笔并发，实测每笔读的耗时：

| | 笔数 | 单笔耗时 p50 | 单笔耗时 max | 单笔带宽 |
|---|---|---|---|---|
| **回退的阻塞整块读** | 7 | **19.4 ms** | 36.8 ms | **71.7 GiB/s** |
| 流式读 | 1 | 33.7 ms | 34.0 ms | 37.0 GiB/s |
| 流式读（全部走流式时） | 8 | 36.0 ms | 44.4 ms | 34.7 GiB/s |

**阻塞读每笔快 1.9 倍。** 而且这不是"阻塞读天生快"——单个请求独占设备时，
流式读是 50.4 GiB/s、阻塞读只有 38 GiB/s，**流式更快**。

差别在 IO 的切分方式。读同样的 1.25 GiB：

```
阻塞整块读：  64 个 extent × 20 MiB
流式读：     640 个 extent × 2 MiB     ← 10 倍多、10 倍小
```

**设备空闲时，小而多是优势**：640 个请求一次性全压下去，队列够深，把 GPFS 喂饱了
（这正是阶段 08 修完空转后 50 GiB/s 的来源）。

**设备已经被别人占满时，小而多变成纯开销**：队列本来就满了，
再多切 10 倍的 IO 只是每个都要走一遍提交、完成、记账的路径。

除此之外，流式路径还多了一层代价（见下节）。

---

## 5. 为什么流式读的带宽会下降

两个原因叠加，一个是上面说的切分粒度，另一个是**层门**。

流式读的设计是"数据边读边喂给计算"，这需要一个层门（`LayerDoneCounter`）
来保证"算第 N 层时第 N 层的数据已经到了"。关键在这段代码：

```python
# cache_controller.py  LayerDoneCounter.wait_until
for index, generation in list(self.stream_consumers.items()):
    ...
    self.events[index].wait(threshold, ...)   # 等每一条打开的流
```

**每一层的计算，都要等所有打开的流都到达这一层。** 于是：

- **槽位 = 1**：只有 1 笔在流式，其余 7 笔走阻塞读——它们的数据在准入前就
  **全部**进了 host 内存，完全不参与层门。整个批次只被 1 条流拖着。
- **槽位 = 8**：8 条流全部挂在层门上，每一层都要等**最慢的那一条**。
  8 条流里只要有一条卡一下，整批计算都停。

这解释了 +249 → +561 ms 这个 2.3 倍的差距，也解释了为什么放开槽位是负优化。

另外，8 笔流式事务各自持有读句柄、各自做分片、各自在 IO 仲裁器里排队，
5120 个 extent 互相挤——而 7 笔阻塞读是被控制器合批处理的。

## 6. 顺带发现一个 bug（未修）

`probe-concurrency=4` + `streams=1` **三轮必现**：
8 个探针全部成功返回之后，引擎再也回不到空闲状态。

```
Cache not flushed because there are pending requests.
  #queue-req: 0, #running-req: 0, blocked_by: ['ongoing_load_back=3']
```

两个 rank 上各留下 **3 笔** H2D load-back 的在途记录，永不消失。

**影响**：`is_fully_idle()` 是 `flush_cache`、`attach`、`detach` 的共同守卫，
一旦有记录泄漏，这三个操作**永久失败**。

**原来的日志查不出来**：它只打队列和运行中的请求数，两个都是 0，
却说"有未决请求"。这次先给那条警告加了 `blocked_by:`，
把所有阻塞子句连同数量一起打出来，一轮就定位到了
（commit `d383d4f738`）。

**已排除**：TP 分歧（两 rank 都是 3）、层门槽位耗尽（无相关报错）、请求失败
（8 个探针 TTFT 都正常）。
**未查清**：这 3 笔对应哪些请求。`pc4-s1` 每波正好 3 笔回退，数字吻合，
但 `pc8-s1` 有 7 笔回退却不复现，所以"回退导致"这个解释站不住。

## 7. 结论与建议

1. **并发会让 L3 相对 L2 的差距从 180 ms 涨到 249 ms**，超过 200 ms。
2. **`--hicache-storage-max-concurrent-streams` 保持默认 1。**
   放开到 8 是 2.3 倍恶化。代码上早就支持多并发，但不该开。
3. **尾部问题已经解决**：阶段 06 的 max +6.2 秒不再出现，
   Δmax ≈ Δp50。
4. **瓶颈仍然是准入那一轮调度会合**，并发只是在它之上叠加。
   真正的解法还是阶段 08 §6 说的：把预取提前，让读在请求到达调度器之前就完成。

---

## 8. 不确定的地方

1. **+180 → +249 这 69 ms 没有精确拆解。** queue/forward 拆分工具在并发下失效了：
   8 个探针被分到不同批次准入，排在后面的排队时间长、等待时间短，
   跨探针取中位数之后两者不再可加（实测出现 "准入 +980 ms、forward −767 ms"
   这种互相抵消的数）。那个工具是为"逐个发探针"设计的。
2. **§5 的层门解释是代码推的，不是测出来的。** 机制在代码里是明确的
   （`wait_until` 确实遍历所有打开的流），但因为上一条，
   我无法用测量确认这 312 ms 确实落在 forward 里。
3. **§4 的"per-IO 开销"解释同样是推断。** 我测到的是单笔读耗时
   （19.4 vs 36 ms）和 IO 切分方式（64×20 MiB vs 640×2 MiB），
   没有测每个 IO 的服务时间，也没有测设备聚合吞吐。
4. **`pc4-s1` 那一档没有数据**（三轮都崩在 §6 的 bug 上）。
5. **每档单次运行。**
6. **绝对 TTFT 仍不代表生产性能**：服务端沿用单请求基准的配置
   （关闭分块预填充、triton 后端、无 CUDA graph）。两臂同配，相对差值可信。

```bash
cd /home/lpl/sglang/benchmark/hicache
/home/lpl/sglangtest/.venv/bin/python bench_steady_state_l3_probe.py \
  --server l3_fused --io-threads 8 \
```
