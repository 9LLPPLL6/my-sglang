# 混合负载下 L2 请求和 L3 请求的端到端 TTFT

2026-09-24 · Llama-3.3-70B-Instruct-FP8，TP=2 · GPFS `/zion0`，O_DIRECT · L3 读走 **NIXL POSIX**

---

## 一句话结论

一批 8 个请求同时发出，4 个前缀在内存里、4 个只在 GPFS 上：

| | n | **TTFT 均值** | 标准差 | queue | forward |
|---|---|---|---|---|---|
| **命中 L2 的请求** | 12 | **1154.0 ms** | 46.3 | 7.8 | 1074.8 |
| **走 L3 的请求** | 12 | **2329.6 ms** | 44.7 | 1249.9 | 1018.1 |
| 差 | | **+1175.6 ms** | | +1242.1 | **−56.7** |

**两个方向的结论：**

1. **L2 请求完全没被拖累。** queue 7.8 ms，和纯 L2 负载下的 7.5 ms 一样。
   同一批里有 4 个请求正在读 GPFS，也没有推迟它们进批次。
2. **L3 请求慢 1175.6 ms，但其中只有约 175 ms 是 L3 路径自己的开销。**
   剩下约 1075 ms 是**排在 L2 那批后面等它跑完 forward**。
   **读盘本身只要 29.8 ms。**

## 怎么读这份报告

### 三个时间指标

```
客户端发出
   │
   ├── 入队 ────────────────────────┐
   │                                │  queue      排队：等调度线程把它编进一个批次
   ├── 进入 prefill 批次 ───────────┘
   │                                │  forward    前向：真正跑模型，含把 KV 搬进显存
   ├── 第一个 token 吐出 ───────────┘
   │
  TTFT = queue + forward + 客户端往返
```

- **TTFT**：客户端侧测的，从发出请求到收到第一个 token
- **queue**：服务端埋点，`forward_entry_time − wait_queue_entry_time`
- **forward**：服务端埋点，准入到完成

**forward 基本正比于批内请求数**，所以比较 forward 前必须确认两边批次形状相同。
本实验两批形状完全相同（见 §4），所以可比。

### 分层判定

每个请求返回时服务端报它的前缀从哪来，按这个**实测**归类，不按设计假设。
本实验 24 个探针全部精确：命中 L2 的 `host=16384 storage=0`，
走 L3 的 `host=0 storage=16384`，零 HBM 污染。

### 所有数字都是均值

没有中位数。每处标了 n。本实验离散度很小（标准差 45 左右，对 1154/2330 的均值），
均值可代表分布。

## 2. 实验怎么做的

一次运行 = 起一次服务端，跑一次 8 探针并发。总共跑了 3 轮。

```
1. 启动服务端（L3 后端开着，引擎 NIXL POSIX）
2. flush_cache 清空所有缓存
3. 预热 8 条前缀（各 16384 token）
   —— write_through 顺带把它们全部写进盘
4. 等写回完成                          实测每轮都是正好 20.00 GiB
5. flush_cache 再清一次
   —— 内存和显存清空，**盘上的 8 条文件不动**
6. make_store_cold 打冷操作系统页缓存
   —— 否则"从盘读"读的是内存
7. 把其中 4 条重新读回内存            ← 这 4 条之后命中 L2
   —— 剩下 4 条一条都不读回            ← 之后只能走 L3
8. evict_device 灌填充数据把它们挤出显存
   —— 内存池是显存池的 6 倍，所以内存副本留得住
9. 启动 6 路背景解码请求，等 8 秒让它稳下来
10. 8 个探针一次性并发发出
11. 记 TTFT 和分层；用请求 id 去日志里把 queue 和 forward 对上
12. 逐个探针校验分层，关服务端
```

**第 5 步能成立的前提**：`flush_cache` 只清显存和内存，**不动盘上的文件**。
所以"再 flush 一次"就把同一批前缀从"在内存里"变成了"只在盘上"。

**为什么不能只用一组前缀**：同一条前缀从盘上读过一次就进内存了，
第二次再用它就变成 L2 命中。所以必须在发请求**之前**把两组摆好。

## 3. 逐轮结果

| 轮次 | L2 TTFT | L3 TTFT | **差** | 背景吞吐 | 写回 | 磁盘读 |
|---|---|---|---|---|---|---|
| 第 1 轮 | 1218.8 | 2390.1 | **+1171.3** | 43.5 tok/s | 20.00 GiB | 10.00 GiB |
| 第 2 轮 | 1114.1 | 2284.1 | **+1170.0** | 44.1 tok/s | 20.00 GiB | 10.00 GiB |
| 第 3 轮 | 1129.2 | 2314.6 | **+1185.4** | 44.2 tok/s | 20.00 GiB | 10.00 GiB |
| **合并** | **1154.0** | **2329.6** | **+1175.6** | | | |

**三轮的差是 1171.3 / 1170.0 / 1185.4，散布只有 15 ms。** 可复现性很好。

绝对值有波动（L2 从 1114 到 1219），但**差值稳定**——说明波动来自服务端整体状态
（背景请求的进度、显存碎片等），不来自 L2/L3 这个变量。

磁盘读每轮都是正好 **10.00 GiB** = 4 条 x 2.5 GiB，一分不差，
说明只有该走 L3 的那 4 个真的读了盘。

## 4. forward 可比，而且 L3 更快

两批的形状**完全相同**：

```
L2 那批：Prefill batch, #new-seq: 4, #new-token: 2048, #cached-token: 65536, token usage: 0.45
L3 那批：Prefill batch, #new-seq: 4, #new-token: 2048, #cached-token: 65536, token usage: 0.45
```

同样 4 个请求、同样 65536 个缓存 token、同样 6 路背景在跑。所以：

| | forward |
|---|---|
| L2 那批 | 1074.8 |
| L3 那批 | **1018.1** |
| 差 | **−56.7** |

**从 L3 读 KV 没有让计算变慢，反而快 57 ms。**
原因是流水线在准入阶段就逐组发起了内存→显存的搬运，forward 开始时已经搬了一部分；
L2 命中走的是 forward 期间的 `load_back`。**是重叠，不是速度。**

## 5. 那 1250 ms 的 queue 里，只有 30 ms 是读盘

把 L3 请求的排队时间按埋点拆开（n=12，三轮合并，均值）：

| 段 | 时长 | 占比 |
|---|---|---|
| **入队 → 提交读** | **1113.5 ms** | **89%** |
| 提交读 → 宣布可准入 | 44.3 ms | 4% |
| 宣布可准入 → 真正进批次 | 92.1 ms | 7% |
| 合计 | 1249.9 ms | |

**读盘本身只要 29.8 ms**（n=48，每笔事务每 rank 一条，量的是整条前缀 10 个组、
32 个 page、640 个 extent、1.25 GiB/卡；带宽 39.5 GiB/s）。

### 那 1113.5 ms 是怎么来的

```
1113.5 ≈ 1074.8（L2 那批的 forward）+ 约 39
```

**提交读这件事跑在调度线程上**，而调度线程正在跑 L2 那批的 prefill。
L3 请求连"开始读"都得等 L2 那批算完。

### 于是 +1175.6 ms 的完整构成

```
~1075 ms   排在 L2 批次后面 —— 调度线程在跑它的 forward，读提交不了
   ~39 ms   那一轮剩下的部分
    44 ms   提交读 → 就绪（其中实际读盘 29.8 ms）
    92 ms   就绪 → 进批次（设备分配、树插入、开 H2D 会话）
   −57 ms   forward 更快，抵消一部分
  --------
 +1176 ms
```

**L3 路径自己只花了约 175 ms，其余约 1075 ms 是在等 L2 那批。**

## 6. 两个对照

### 和"全部走 L3"比

| 场景 | L3 请求的 queue |
|---|---|
| 8 个探针**全部**走 L3（前面没有 L2 批次挡路） | **514.3 ms** |
| 本实验：4 个 L2 + 4 个 L3 | **1249.9 ms** |

差出来的约 736 ms 就是"排在 L2 批次后面"的代价。

> 严格说这两组探针数不同（8 vs 4），不是精确对照，但方向和量级清楚。

### 和"全部命中 L2"比

| 场景 | L2 请求的 queue |
|---|---|
| 8 个探针全部命中 L2，**不开** L3 后端 | 7.5 ms |
| 8 个探针全部命中 L2，**开着** L3 后端 | 4.3 ms |
| 本实验：同一批里有 4 个正在读 GPFS | **7.8 ms** |

**三者一致。挂上 L3、而且同批有请求正在读盘，都不影响命中 L2 的请求进批次。**

## 8. 不确定的地方

1. **两组不在同一个 prefill 批次里，这是混合负载的真实行为，不是测量假象。**
   但解读时要知道 +1176 ms 里约 1075 ms 是"排在 L2 批次后面"，不是读盘。
2. **每组 n=12（3 轮 x 4 个）。** 组内离散度极小，但轮数只有 3。
3. **只测了 50/50 一个比例。** 少数 L3（比如 8 选 2）会不会让阻塞变短，没测。
4. **没测过 L3 批次排在前面的情况。** 本实验里 L2 总是先进批次（它排队只要 7.8 ms），
   所以 L3 总是排在后面。如果预取能提前跑完，顺序可能反过来，没验证。
5. **绝对 TTFT 不代表生产性能**：关闭了 CUDA graph 和分块预填充。两组同配，相对差值可信。
6. **§6 的两个对照探针数不同**（8 vs 4），只能看方向和量级。

## 9. 怎么复现

```bash
cd /home/lpl/sglang/benchmark/hicache
/home/lpl/sglangtest/.venv/bin/python bench_mixed_l2_l3.py \
  --server-arms mixed_nixl --probes 8 \
  --page-size 512 --hit-tokens 16384 --suffix-tokens 512 \
  --background-requests 6 --io-threads 8 --max-concurrent-streams 8 \
  --max-total-tokens 163840 --hicache-ratio 6.0 \
  --store-root /zion0/kv-aio-bench/<独立目录> --run-id <名字>
```

- `mixed_nixl` 这个臂在 `ARM_SPEC` 里定义为 `("l3_nixl", 0.5)`，
  即服务端用 NIXL 引擎、一半探针走 L3。改比例就改这个 0.5。
- **`--max-concurrent-streams 8` 不能省**（默认是 1，超出的请求会退回阻塞整段读）。
- 每轮用**独立的 `--store-root`**。三个臂共用 store 会让第二个臂的写回增长为 0，
  而等待写回是按增长判定的，会死等超时。
