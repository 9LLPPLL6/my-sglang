> 阶段 02 证明了流水线能把 L3 的读取藏起来。
> 这一阶段回答两个问题：**藏到什么程度**（离纯 L2 命中还差多少），
> 以及**换一种存储之后还成不成立**。

---

## 1. 一句话结果

同一份代码，两种存储，结论相反。

相对纯 L2 命中的额外开销（S/H ≥ 0.3，即有计算可掩盖）：

| 模式 | 本地 NVMe | GPFS |
|---|---|---|
| 旧后端 `file` | 559–570 ms | 无法测量（见 §6） |
| 新后端 `layerwise_file`，关流水线 | 387–415 ms | **27–35 ms** |
| 新后端 `layerwise_file`，开流水线 | **47–87 ms** | **67–150 ms** |

- 在**本地单块 NVMe**（3.45 GiB/s）上，流水线把 402 ms 压到 64 ms，净省约 340 ms。
- 在 **GPFS**（并发可到 60.8 GiB/s）上，读取本来只要 32 ms，**没有延迟可藏**，
  开流水线反而多花 40–115 ms。

**流水线的价值完全由存储读带宽决定。**它的收益是被藏起来的读取时间，
代价是自身固定开销（分组提交、层门等待、admission 往返），实测约 70 ms。

## 2. 实验配置

### 模型与 KV

| | |
|---|---|
| 检查点 | `nvidia/Llama-3.3-70B-Instruct-FP8`（ModelOpt 0.27.1），盘上 68 GB |
| 权重量化 | FP8 |
| **KV cache 数据类型** | **FP8，1 字节/元素**（`hf_quant_config.json` 里 `kv_cache_quant_algo: FP8`） |
| 层数 / KV 头数 / head_dim | 80 / 8 / 128 |
| 并行 | TP=2，2× RTX PRO 5000 72GB Blackwell |
| page-size | 64 token |

**注意 KV 是 FP8 而不是 bf16。**我一开始按 bf16 估算，落盘字节数差了整两倍，
写穿等待的门槛因此永远等不到，实验直接超时失败。

### 页文件大小是怎么来的

```
每 token KV     = 2 (K,V) × 80 层 × 8 头 × 128 dim × 1 B = 163 840 B (160 KiB)
每 rank 每 token = 163 840 ÷ 2 rank                       =  81 920 B  (80 KiB)
每页 (64 token)  = 64 × 81 920                            = 5 242 880 B = 5.00 MiB
前缀 8832 token  = 138 页 × 2 rank = 276 个页文件           = 1.348 GiB
```

两个后端的页文件实际大小（`stat` 结果）：

| 后端 | 单个页文件 | 盘上布局 |
|---|---|---|
| stock `file` | 5 242 880 B（正好 5.00 MiB） | 扁平目录，`<hash>_<model>_<rank>_<world>.bin` |
| `layerwise_file` | 5 243 392 B（5.00 MiB **+ 512 B 页头**） | `format-v1/<id>/tp-2/rank-N/<xx>/<hash>.kv` |

整段前缀在盘上是 `276 × 5 242 880 = 1 447 034 880 B`（stock）
或 `276 × 5 243 392 = 1 447 176 192 B`（layerwise）。
**每次计时请求实测从块设备读取的字节数与这两个值逐字节相符**——这是层级隔离的核心证据。

顺带一提：GPFS 块大小是 4 MiB，而页文件是 5 MiB + 512 B，并不对齐。

### 存储

| | |
|---|---|
| 本地 | `/dev/nvme4n1p3`，ext4 |
| GPFS | `fs0`，56 TiB，挂在 `/zion0`，块大小 4 MiB |

### 六个 arm

| arm | 含义 |
|---|---|
| `l1` | 前缀留在显存 → 地板值，TTFT 只剩后缀计算 |
| `l2` | 无 storage 后端的服务器上，前缀被 filler 挤出显存 → 纯 host 命中 |
| `l2_fused` | **同一个融合服务器内**的纯 host 命中 |
| `l3_old` | stock `file` 后端，`wait_complete` |
| `l3_nopipe` | `layerwise_file` + `load-mode full_wait`（新后端，关流水线） |
| `l3_fused` | `layerwise_file` + `load-mode layerwise`（新后端，开流水线） |

`load-mode` 和 `storage-backend` 都是启动参数，改不了，所以四种配置是**四次串行启动**，
不是四台机器。

`l2_fused` 是必须的：`l2` 跑在没有 L3 的服务器上，拿 `l3_fused` 减 `l2`
会同时混入层级差异和启动配置差异。`l2_fused` 消掉后者，层级成为唯一变量。
实测两者只差 **1–18 ms**——把整套 L3/融合机制打开，对一个普通 L2 命中几乎没有代价，
和 §02-6 里「6 个 hook、关掉开关原路径不变」的说法一致。

## 3. 两种存储的裸读带宽

并发 O_DIRECT `pread` 同一个 4.00 GiB 文件，逐步加并发：

| 并发 reader | 1 | 2 | 4 | 8 | 16 | 32 | 64 |
|---|---|---|---|---|---|---|---|
| **GPFS** GiB/s | 6.92 | 12.13 | 20.59 | 37.26 | 60.13 | **60.80** | 59.41 |
| **NVMe** GiB/s | 3.26 | 3.44 | 3.45 | 3.44 | 3.45 | 3.45 | 3.44 |

GPFS 随并发线性扩展，16 路即饱和在 60 GiB/s；本地单盘 1 路就打满，之后完全平坦。
所有采样点 `read_bytes` 都是 1.00×，即真实块层 I/O。

这条曲线解释了 §1 的全部结果：**本地是一块盘，GPFS 是一个并行文件系统。**

---

## 4. 各模式实际达成的读带宽

把每种模式相对纯 L2 多花的时间，换算成搬动这 1.348 GiB 的等效带宽：

| 模式 | NVMe 暴露耗时 | 等效带宽 | 占上限 | GPFS 暴露耗时 | 等效带宽 | 占上限 |
|---|---|---|---|---|---|---|
| 旧后端，首次加载 | 1030 ms | 1.31 GiB/s | 38 % | — | — | — |
| 旧后端，稳态 | 565 ms | 2.39 GiB/s | 69 % | — | — | — |
| 新后端，关流水线 | 402 ms | **3.35 GiB/s** | **97 %** | 32 ms | **41.8 GiB/s** | 69 % |
| 新后端，开流水线 | 64 ms | 21.0 GiB/s※ | 6.1× | 78 ms | 17.3 GiB/s※ | 0.28× |

※ **表观**带宽。读取并没有变快，而是被计算盖住、离开了 TTFT，所以可以超过设备上限；
这正是流水线起作用的标志。

- 关流水线时，新后端在本地盘吃到设备的 **97%**——读路径本身已经没有余量可挤。
- 在 GPFS 上它达成 **41.8 GiB/s**，落在裸带宽曲线 8 路（37.3）与 16 路（60.1）之间，
  和它的 AIO 在途深度相符。
- 开流水线后，本地盘表观带宽是设备上限的 6.1 倍；而在 GPFS 上表观带宽
  **低于**同后端不开流水线的值——净损耗。

## 5. TTFT 明细

S 是缓存前缀之后新增的后缀长度，决定有多少计算可以用来掩盖读取。H = 8832。

### 本地 NVMe（run `llama-nvme-full`，24/24 通过验证）

| 后缀 S | S/H | l1 | l2 | l2_fused | l3_old | l3_nopipe | l3_fused | 融合 − L2 |
|---|---|---|---|---|---|---|---|---|
| 64 | 0.01 | 104 | 113 | 122 | 1152 | 532 | 443 | +321 |
| 2688 | 0.30 | 1090 | 1105 | 1110 | 1679 | 1525 | 1168 | **+59** |
| 4416 | 0.50 | 1795 | 1817 | 1822 | 2388 | 2209 | 1909 | **+87** |
| 8832 | 1.00 | 3832 | 3866 | 3881 | 4439 | 4276 | 3928 | **+47** |

### GPFS（run `llama-gpfs-01`）

| 后缀 S | S/H | l1 | l2 | l2_fused | l3_old | l3_nopipe | l3_fused | 融合 − L2 |
|---|---|---|---|---|---|---|---|---|
| 64 | 0.01 | 103 | 114 | 132 | (756) | 167 | 282 | +150 |
| 2688 | 0.30 | 1089 | 1106 | 1112 | (1268) | 1147 | 1192 | **+80** |
| 4416 | 0.50 | 1797 | 1818 | 1819 | (1974) | 1852 | 1906 | **+87** |
| 8832 | 1.00 | 3839 | 3869 | 3882 | (4036) | 3909 | 3948 | **+67** |

`l3_old` 那一列加括号：它们**不是从 NVMe 读来的**，被验证器拒收，不参与任何结论（见 §6）。
GPFS 表里 `l1`/`l2` 是 n=2（GPFS 未挂载时崩掉的那次已跑完无存储服务器，记录追加进同一目录），
两次取值一致；其余单元格 n=1。

S=64 那一行没有计算窗口，融合路径在本地盘仍要背 321 ms：
读盘无处可藏，只能把读完之后的尾巴塞进读取期间——和 §02-10 的结论一致。

## 6. 层级隔离是量出来的

要求是：命中不能来自 HBM；测 L3 时不能来自 host 内存，也不能来自任何读缓存。
每次测量三个独立探针，任一项不符即整条记录作废、不进平均。

| 探针 | 做什么 |
|---|---|
| **层级归属** | 逐请求回读 `meta_info.cached_tokens_details` 的 device / host / storage 命中长度 |
| **块设备实读字节** | 服务器整个进程树的 `/proc/<pid>/io` 里 `read_bytes`，计时请求前后各采一次。它只统计真正从块层取到的字节，page cache 命中记 0 |
| **落盘文件驻留量** | `mincore()` 扫整个 L3 store，配合 `fadvise` 循环直到驻留归零 |

实测结果（本地 NVMe）：

| arm | device / host / storage | 块设备实读 | 判定 |
|---|---|---|---|
| `l1` | 8832 / 0 / 0 | 0.00× | 通过 |
| `l2`、`l2_fused` | **0** / 8832 / 0 | 0.00× | 通过 |
| `l3_old`、`l3_nopipe` | 0 / **0** / 8832 | 1.00× | 通过 |
| `l3_fused` | **0** / 8832（staged） / 0 | 1.00× | 通过 |
| `l3_old` on GPFS | 0 / 0 / 8832 | **0.00×** | **拒收 ×4** |

块设备实读字节数还是**唯一能区分真 L2 命中和流式 L3 命中的手段**：
融合服务器上桥接层把 staged prefetch 也记作 host 命中（§02-4），两者层级数字完全一样。

### 两个方法上的坑

**一、每次测量必须换新前缀。**
若复用前缀，预热请求本身会变成一次 L3 **读取**，在计时读之前几秒把缓存重新填满。
用新前缀则预热永远是写入，`sync + fadvise` 之后 store 确实是冷的，而 `mincore` 会证明这一点。

**二、写穿落盘的等待门槛要用增量，不能用绝对值。**
store 里已经有前几次测量的数据，绝对阈值会被立刻满足，于是在本次前缀真正落盘之前就放行了。

### 为什么旧后端在 GPFS 上测不了

GPFS 把文件数据缓存在自己的 **pagepool** 而不是 Linux page cache。对缓冲 I/O 来说三样探针全废：

| 探针 | 本地 NVMe (ext4) | GPFS |
|---|---|---|
| `mincore` 驻留量 | 有效，2048 → 0 → 2048 MiB | **恒为 0** |
| `fadvise(DONTNEED)` | 有效，驻留归零 | **空操作** |
| 缓冲读三次连读（2 GiB） | 591 / 120 / 591 ms | **169 / 170 / 170 ms** |
| 缓冲读 `read_bytes` | 1.00× 冷 / 0.00× 缓存 | **恒为 0.00×** |
| O_DIRECT 单线程 | 625 ms，3.20 GiB/s，1.00× | 553 ms，3.62 GiB/s，1.00× |

GPFS 上缓冲读三次都是 11.8 GiB/s，即每次都从 pagepool 出。
**只有 O_DIRECT 既绕过 pagepool 又可验证**——新后端正是 O_DIRECT，旧后端不是。

所以脚本做成 fs 感知：检测到 `gpfs` 就不再拿 `mincore` 当证据（那是空洞的），
标记 `page_cache_governed = false`，改由块设备字节数兜底。旧后端因此被明确拒收，
而不是悄悄给出一个 pagepool 的漂亮数字。

> 补充一句公平的话：如果生产环境就是 GPFS，旧后端确实能吃到 pagepool 的加速。
> 但那不是从 L3 加载的性能，而且这里 1.348 GiB 的前缀恰好小到必然全中——
> 前缀更大时这个便宜就不成立了。

## 7. 旧后端的一次性首读开销

按理说两个后端的差值只取决于读取字节数，与后缀长度无关。
但 §5 表里 `l3_old` 在 S=64 处的缺口（1030 ms）明显大于其他后缀（约 565 ms）。
两个实验把原因定了下来。

**同一服务器，固定 S=2688，连测 5 次**（run `llama-firstread`）：

| arm | 第 1 次 | 2 | 3 | 4 | 5 | 稳态均值 |
|---|---|---|---|---|---|---|
| `l3_old` | **2142** | 1678 | 1672 | 1675 | 1670 | 1674（首次 **+468 ms**） |
| `l3_nopipe` | 1512 | 1505 | 1525 | 1522 | 1513 | 1515（无，极差 19 ms） |

**倒序执行**（run `llama-nvme-rev`）：

| 执行顺序 | S=8832（第 1 次） | S=4416 | S=2688 | S=64（最后） |
|---|---|---|---|---|
| `l3_old` | 4895 | 2382 | 1674 | 687 |
| `l3_nopipe` | 4280 | 2228 | 1512 | 517 |
| 差值 | **615** | 154 | 162 | 170 |

正序时 615 ms 的大缺口在 S=64，倒序时它**跟着「第一次测量」搬到了 S=8832**，
S=64 变成 170 ms。所以它取决于执行顺序，不取决于后缀长度；
5 次重复进一步表明是**一次性**的。

结论：旧后端首次走存储加载路径有一次性初始化开销（约 468 ms），新后端没有。
**稳态的后端提升是 158 ms（2.39 → 3.35 GiB/s），与后缀长度无关。**

> 这个数字我归因错了两次。先说是 page cache 补贴了后面几次——被「四次全部 1.00×
> 真实读盘」推翻；再说是为 1.38 GiB 新申请 page cache 页的成本——被 5 次重复推翻
> （每次测量前 store 都已清冷，若是分配成本就该每次都付）。
> 教训和 §02-10 一样：拆性能数字要设计对照组，不要推。

## 8. 什么时候该开流水线

流水线把「相加」变成「取最大值」：读取不再是首字延迟前的一道硬墙，而是与后缀计算重叠。

- **读取远大于自身开销时，开。** 本地单盘读取 402 ms，压到 64 ms，净省约 340 ms。
- **读取已经很快时，关。** GPFS 上读取只有 32 ms，开启后反而多花 40–115 ms。
- **盈亏平衡在有效读带宽约 19 GiB/s**（1.348 GiB ÷ 70 ms）。随前缀长度变化：
  前缀越长，平衡点越高，流水线适用范围越宽。
- **没有计算窗口时收益有限。** S=64 时本地盘仍要背 321 ms。

建议：不要无条件打开 `--hicache-storage-load-mode layerwise`，
按启动时实测的读带宽（或预估读取时间与自身开销之比）来决定。

## 9. 怎么复现

```bash
cd benchmark/hicache

# 本地 NVMe
python3 bench_l2l3_fusion_ttft.py --run-id nvme --store-root /home/lpl/l3-run-llama

# GPFS
python3 bench_l2l3_fusion_ttft.py --run-id gpfs --store-root /zion0/kv-aio-bench/l3-run-llama

# 只看某几个 arm / 换后缀 / 加重复
python3 bench_l2l3_fusion_ttft.py --arms l3_old,l3_nopipe --suffixes 2688 --reps 5

# 重看汇总
python3 bench_l2l3_fusion_ttft.py --analyze results/l2l3_fusion/<run_id>
```

脚本自己从所在位置推出 `PYTHONPATH=<repo>/python`，测的就是本 checkout 的代码。

这台机器上有三个环境前提：

1. JIT 内核要 shell 出 `nvcc`，而 `/usr/bin/nvcc` 是 CUDA 12.0，编不了 sm_120a
   （FP8 检查点需要）。脚本默认把 `/usr/local/cuda-13.0/bin` 放到 PATH 前面，
   和 torch 的 cu130 对齐（`--cuda-bin-dir` 可改）。
2. 已装 flashinfer 0.6.14 旧于 checkout 预期，FP8 warmup 时 autotuner 导入失败。
   脚本默认加 `--disable-flashinfer-autotune`（autotune 只挑内核变体，不影响正确性）。
3. `--kv-bytes-per-token` 默认按 Llama-3.3-70B 的 FP8 KV 算（163 840）。换模型要改。
