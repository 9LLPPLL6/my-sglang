## 一、实验流程

两个臂（L2 / L3）在**同一个服务进程内先后跑**，配置完全相同，唯一差别是前缀被放在哪一层。每个臂五步：

### ① 预热：把前缀写进存储

```
flush_cache（清空所有层级）
  ↓
8 条前缀，每条 16384 token，逐条写入
  每条分步扩展（每步 ≤ 16384 token），避免单次预填充过大
  ↓
等待写回存储完成：存储增长 20.00 GiB ✓
```

8 条前缀互不相同，**探针之间零前缀共享**——一个探针不会读到另一个探针刚拉进来的数据。

### ② 造场景：决定前缀在哪一层

| | 做法 | 结果 |
|---|---|---|
| **L2 臂** | 用填充请求灌满设备 KV 池，LRU 把前缀挤出 HBM | host 内存里还有副本（host 池是设备池的 6 倍，挤不掉） |
| **L3 臂** | `flush_cache` 清空 HBM + host | 只剩存储里那一份 |

### ③ 背景请求：让服务端处于"正在推理"状态

```
6 个请求，每个：输入 512 token，输出 20000 token
持续 decode，中途不会重新预填充
等 8 秒进入稳态
```

目的是制造真实场景：**新请求到达时，GPU 正在为别的请求做 decode**，L3 预取才有机会和调度重叠。背景请求在②之后才启动——更早会被 `flush_cache` 冲掉，更晚则污染命中层级的归属。

### ④ 探针：逐个发，测 TTFT

```
8 个探针，一个一个发，每个之间隔 2 秒
每个探针 = 自己的 16384 前缀（命中）+ 5120 个新 token
max_new_tokens = 1（只测首 token）
```

逐个发而不是一起发，是为了让每个探针都落在"背景请求正在 decode"的中间状态里。

### ⑤ 校验：每个探针的命中层级都断言

这个实验最容易悄悄失效的方式是：背景请求把探针前缀挤出了 L2，于是"L2 臂"其实读的是存储。所以每个探针的返回都检查：

- **L2 臂**：出现 `storage > 0` → 报错，这不是 L2 测量
- **L3 臂**：出现 `device > 0` → 报错，HBM 没清干净

本次运行零告警。

## 二、请求调度流程

三类线程各司其职：

| 线程 | 数量 | 职责 |
|---|---|---|
| **调度线程** | 每个 TP rank 一个 | 收请求、建批次、跑 forward、处理结果。**所有准入决策只在这里做** |
| **预取线程** | 1 | 问存储"这些 page 在不在"，不搬数据 |
| **IO 线程** | 8 | 真正从 GPFS 读数据到 host 内存 |

调度线程是一个循环，一轮做一件事：

```
收请求 → 建批次 → 跑 forward → 处理结果 → 收请求 → ...
                   └─ 背景请求在 decode，约 150 ms
```

**准入只发生在"建批次"这一步**，一轮一次。forward 期间调度线程被占住，无法准入任何请求。

### 一个探针的完整时间线

```
时刻   调度线程                              预取线程         IO 线程 ×8
════════════════════════════════════════════════════════════════════════
 t0    收到探针请求
       ├ 入队
       └ 发起存储查询  ───────────────────►  查 page 在不在
       建批次（探针的预取还没有结果）
       跑 forward ──────────── 约 150 ms ────────────────────────────
                                            查完，结果入队
────────────────────────────────────────────────────────────────────────
 t1    建批次前：
       ├ 排空存储命中队列
       │   分配 host 内存
       │   提交读取  ──────────────────────────────────────►  开始读
       ├ 检查预取进度 → 读刚开始，未完成
       └ 建批次                    ◄══ L2 探针在这一轮被准入 ══
       跑 forward ──────────── 约 150 ms ────────────────────────────
                                                            读完（25 ms）
                                                            之后空闲
────────────────────────────────────────────────────────────────────────
 t2    建批次前：
       ├ 排空存储命中队列
       ├ 检查预取进度 → 已完成
       └ 建批次                    ◄══ L3 探针在这一轮被准入 ══
       跑 forward（探针自己的 prefill，约 2.5 秒）
════════════════════════════════════════════════════════════════════════
```

### 两个关键时间点

**L2 准入点 = t1。** 前缀已在 host 内存，没有任何东西要等，请求进队后的第一个"建批次"就被准入。

**L3 预取的三个时间点：**

| | 时刻 | 在哪个线程 |
|---|---|---|
| 查询存储有没有 | **t0**（入队时立刻发起） | 预取线程 |
| **提交读取**（读真正开始） | **t1** | 调度线程 |
| 发现读完、准入 | **t2** | 调度线程 |

**L3 比 L2 晚一轮，原因在这里**：读取是在 **t1** 才开始提交的，而 t1 正是 L2 被准入的时刻。读本身只要 25 ms，在 t1 到 t2 之间早就完成了，但**只有调度线程能发现它完成了，而它要到 t2 才回来看**。

所以这 164 ms 是**一轮调度的往返**，不是存储慢。
