# HiCache L3 在 GPFS 上的 TTFT：慢在哪里，以及修掉了什么

| | |
|---|---|
| 日期 | 2026-09-18 |
| 模型 | Llama-3.3-70B-Instruct-FP8，TP=2 |
| 存储 | GPFS `/zion0`，O_DIRECT |
| 负载 | 稳态：6 个背景请求持续 decode，8 个探针逐个到达 |
| 探针 | 前缀 16384 token（命中）+ 5120 token（新），page 512 |
| 分支 | `L2-L3fusion-continuous-read` |
| 详细记录 | [阶段 07](07-steady-state-and-what-the-pipeline-costs.md)、[阶段 08](08-where-the-180ms-actually-goes.md) |

---

## 摘要

**问题**：同样的前缀，从 L3（GPFS）取比从 L2（host 内存）取，TTFT 慢约 180 ms。之前不知道这 180 ms 花在哪，因此不知道该优化什么。

**结论**：慢的不是存储。

- **forward 阶段零暴露**：7 组配置全部在 −2 ~ −18 ms。担心的"算到第 N 层、第 N 层数据还没到"**没有发生**。
- **读快 6.9 倍，TTFT 一毫秒没省**。
- **代价是一次调度往返**：请求要多等调度线程来看它一次，实测 140–170 ms。**与存储多快无关。**

**已修复**：读取过程中设备空转 132 ms 的缺陷。读取从 171 ms 降到 25 ms，带宽从 7.3 GiB/s 提到 **50.1 GiB/s**（超过原有阻塞读路径的 38 GiB/s）。这项修复买回的是设备利用率，不是延迟。

**下一步**：要动 TTFT，只能修准入时机。两条路，代价差别很大，见第 6 节。

---

## 1. 测量方法

以前只能看到端到端的 TTFT，无法判断时间花在排队还是计算。这次用上游已有的、每个请求的三个时间戳把它切开：

```
入队  ──────────►  准入进 prefill 批  ──────────►  完成
      queue_duration                forward_duration
```

- **`queue_duration`**（入队 → 准入）：L3 的预取等待**只可能**在这一段
- **`forward_duration`**（准入 → 完成）：数据没跟上导致的计算阻塞**只可能**在这一段

这个切分不需要改动推理逻辑，只需打开一个已有的日志开关。两臂（L2 / L3）用完全相同的服务端配置、相同的探针、在同一个服务进程内先后跑，只有前缀所在层级不同。

另外给存储读补了两个时间戳（读开始 / 读结束），和上面的时间戳同一个时钟，因此**时间线是减出来的，不是推出来的**。

---

## 2. 结论一：forward 阶段零暴露

| 配置 | Δforward（L3 − L2） |
|---|---|
| 阻塞读 | −2 ms |
| 流水线，层组 = 80 | −12 ms |
| 流水线，层组 = 40 | −18 ms |
| 流水线，层组 = 20 | −13 ms |
| 流水线，层组 = 8 | −12 / −16 ms |
| 流水线，层组 = 8（修复后） | −15 ms |

**七组配置无一例外。** 意味着：数据从 GPFS 补进来这件事，被前向计算完全掩盖了。这是一个正面结论——它说明分层流式加载在"掩盖计算"这个目标上是成立的。

补充一点：L2 路径**同样**经过逐层门控（host→device 的拷贝也走同一套计数器）。所以 L3 不是"多了一道门"，只是门后等的东西从 PCIe 变成了 GPFS。两臂 forward 相等，说明这个替换本身不花钱。

---

## 3. 结论二：读得多快，几乎不影响 TTFT

通过调整层组大小，让同一份数据的读取时间变化近 5 倍：

| 层组大小 | 读取耗时 | 读取带宽 | **Δ准入** |
|---|---|---|---|
| 80 | 35 ms | 35.8 GiB/s | +162 ms |
| 40 | 153 ms | 8.2 GiB/s | +170 ms |
| 20 | 158 ms | 7.9 GiB/s | +171 ms |
| 8 | 171 ms | 7.3 GiB/s | +189 ms |

读取时间变化 **136 ms**，TTFT 只变化 **27 ms**——**80% 被吸收了**。

原因在下面这张表。把"读开始 → 准入"这段时间再拆一层：

| 层组大小 | 读取耗时 | 读完后干等 | **合计** |
|---|---|---|---|
| 8 | 171 ms | −1 ms | **170** |
| 20 | 158 ms | 9 ms | **167** |
| 40 | 153 ms | 15 ms | **169** |
| 80 | 35 ms | 131 ms | **166** |

**这个窗口恒定在 167 ± 2 ms。** 读取省下来的时间，一分不少地变成了等待。

修复空转之后又独立验证了一次：读取从 171 ms 降到 25 ms（快 6.9 倍），Δ准入 186 → 194 ms，**在噪声带内，没有改善**。

---

## 4. 结论三：代价是一次调度往返

用状态机埋点记录了每笔存储读取被调度线程"看到"的次数，8 个探针全部是 **2 次**：

```
入队
  │  ~130 ms
第 1 次访问  ←── L2 的请求就在这一趟被准入
  │  提交存储读取（读从这里才开始）
  │  同一趟里检查预取进度：读刚开始，必然未完成
  │
  │  ~146 ms  ←── 整整一趟。期间无人查看这笔读取，
  │              数据可能 25 ms 就全部就位了，但没人知道
  │
第 2 次访问
  └─ 发现完成 → 准入                ←── 比 L2 晚了整整一趟
```

**关键在顺序**：读取恰好是在 L2 被准入的那个时间点才**开始提交**的。所以存储再快也追不上——"提交完成了"这件事，最早只能在下一个调度点被发现。

这就是那 180 ms 的全部来源，也解释了为什么它对存储速度不敏感。

---

## 5. 已完成的修复：设备空转

埋点暴露出一个独立的缺陷。原实现是"读完第 0 组再提交后续组"，但**只有调度线程能发现第 0 组读完了**，而它一轮才来一次。于是：

```
提交第 0 组  ──►  第 0 组读完  ──────────────►  提交其余组  ──►  全部完成
                              ↑ 设备空转 132 ms
```

171 ms 的"读取"里，约 132 ms 磁盘是闲着的。而且这段空转被算进了带宽的分母，于是报出 7.3 GiB/s——**那是个假带宽**。

**改法**：在打开事务时就把整份读取计划一次性交给 IO 仲裁器，第 0 组用高优先级、其余用低优先级。顺序不再依赖"等一等"来保证，而是由仲裁器的优先级和槽位预留保证。

| | 改前 | 改后 |
|---|---|---|
| 后续组提交时刻 | +135.6 ms | **+5.9 ms** |
| 读取耗时 | 171 ms | **25 ms** |
| 读取带宽 | 7.3 GiB/s | **50.1 GiB/s** |
| TTFT | — | **不变**（预期内） |

50.1 GiB/s 也超过了原有整块读取路径的 38 GiB/s。顺带澄清一个之前的误判：这条路径的小分片（2 MiB）曾被认为是带宽低的原因，实际不是——**一次性全部下发时，小分片反而更快**（队列更深）。

这项修复买回的是设备利用率和一个真实的带宽数字。延迟没动，也不该动。

---

## 6. 还剩什么

数据在 25 ms 就已全部就位，请求还要再等约 145 ms 才被准入。**流水线在当前场景下已经退化成"一次很快的阻塞读"**——后续层组根本没机会边算边补，因为它们在准入之前就全到了。

要继续降 TTFT，只能修准入时机，两条路：

| | 做法 | 收益 | 代价 |
|---|---|---|---|
| **A** | 提交读取后就地等第 0 组落地（有界） | 当场省掉一整趟，惩罚可降到 ~0 | 自旋期间**阻塞调度线程 = 阻塞所有请求**；第 0 组单独读的真实耗时尚未测量，可能超出可接受的等待上限 |
| **B** | 把预取提前到 tokenize 之后 | 同上，且不占调度线程 | 跨 TokenizerManager / Scheduler 进程边界，改动大，TP 一致性与 host 内存归属需重新安排 |

两条路都依赖同一个尚未测量的数字：**第 0 组单独读取到底要多久**。建议先补这一个测量（一轮实验），再决定。

另有一条与本报告结论一致的独立观察：在当前场景下，**关掉流水线的配置反而更省**（+100 ms vs +162 ms）。如果短期内不修准入时机，这是更优的默认配置。

---

## 7. 口径与局限

1. **绝对 TTFT 偏高（约 2.7 秒）**：服务端沿用了单请求基准的配置（关闭分块预填充、triton 后端、无 CUDA graph），是为了让单次读取可归因。两臂配置完全相同，**相对比较可信，绝对值不代表生产性能**。
2. **每档单次运行**。可重复性证据：层组 = 8 跑了三遍，Δ准入为 186 / 189 / 194 ms（跨度 4%）；L2 臂七轮的排队时间落在 129–132 ms。
3. **那次调度往返实测 140–170 ms，但它与 decode 轮次周期的换算关系尚未完全对齐**。不影响上述结论（结论只依赖直接测量值），但这段的内部结构还没完全看清。
4. **第 0 组单独读取的耗时未测**，是第 6 节两条路的共同前提。
5. **背景负载是"短输入 + 长生成"**，不是"不断到达的新请求"。后者对缓存的冲刷更剧烈，更接近生产，尚未测试。
6. **随机 token、请求间零前缀共享**，因此冗余读取的代价没有被测到。真实负载下的结论需要单独验证。

---

## 8. 一页纸总结

- 慢的不是 GPFS，是**准入要多等一次调度往返**，与存储速度无关
- 分层流式加载在"掩盖计算"上是**成功**的（forward 零暴露）
- 已修复一个设备空转缺陷：读取 **171 → 25 ms**，带宽 **7.3 → 50.1 GiB/s**
- TTFT 未改善，且不应期待改善——瓶颈在调度时机，不在 IO
- 下一步需要一次小测量（第 0 组读取耗时）来在两条修法之间做选择
